# 中期冻结审查标准

> 项目铁律：每次中期冻结都必须按本标准完成审查、范围内修复、证据与知识归档，并给出明确的冻结/未冻结结论。冻结表示停止新增范围并进入维护状态，不等于宣称没有已知问题。

## 执行步骤

1. **先立计划**：更新正式计划文档和索引，声明目标、边界、证据来源、不可执行事项、验收标准和负责人决策点；计划变更先更新并按项目流程提交。
2. **锁定基线**：同步远端；记录 commit/tag、分支、工作树状态、版本、依赖与可复现验证命令。保留既有改动。
3. **审查产品**：逐项将公开承诺映射到实现、规则、测试或真实证据；覆盖用户流程、适用范围、失败模式、安全、兼容性、可维护性、测试、打包、发布与支持状态。
4. **审查市场**：按用户任务划分直接竞品和相邻替代品，查阅有日期的一手来源，记录能力、交付面、维护状态、差异和证据局限。不要宣称全球穷尽，除非有可审计的完整市场定义和检索过程。
5. **形成缺口与修复**：按严重性、影响和证据排序；优先修复范围内、可逆且有回归覆盖的问题。新功能必须证明属于既定目标。受删除、历史重写、发布或基础设施政策限制的事项只记录为决策门槛。
6. **清理并沉淀**：清除或更新过期声明、断链、死代码/死文档、重复计划和不一致命名；删除需授权的内容先列清单。保存公开版审查、项目时间线、决策/计划索引、验证记录和可复用知识；隐私材料留在受忽略的私有归档并核实不会打包/发布。
7. **复核与验收**：执行项目既有验证；核对文档链接、包内容、公开隐私扫描、工作树与提交状态；由审查者复核每项结论有证据，未解决项有负责人、条件和状态。
8. **作出冻结决定**：仅当核心范围已交付、没有未处理的高严重度缺陷、发布与维护边界明确、归档可导航且所有剩余事项有明确所有者/批准门槛时，建议维护冻结。否则写明阻塞项，不把项目标为已封存。

## 必备归档

- 一份带合法 frontmatter 的权威冻结计划及当前状态。
- 一份有日期的审查报告：发现、证据、严重度、竞品比较、改进项、未解决事项。
- 一份从产品起点到冻结点的项目时间线，关联版本、主要决策、计划和实现证据。
- 一份知识归档索引：每项原始计划/审计/规格的路径、日期、隐私级别、状态（有效/完成/取代/待决）及权威关系；保留原始材料，标清过期快照。
- 一份可重跑的验证记录：命令、环境、结果、失败/跳过和范围限制。
- 一份未来复启说明：什么条件会重新打开项目、哪些事项必须先获所有者决定。

## 不可妥协

不得为完成归档而静默丢弃资料、泄露私有内容、伪造历史或验证、用本地提交冒充远端完成。破坏性操作、历史重写、对外发布及项目政策限定的改动遵循对应授权要求。冻结后的新工作先更新权威状态和计划。
