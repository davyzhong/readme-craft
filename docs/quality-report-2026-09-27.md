## 3. 修掉的真实问题（不是"为了提分"）

### 3.1 FLOW — 事实性错误（最严重）

README 原文声称按「**16 铁律 + 10 反模式 + 80 分量表**」适配，
实际当前规范是 19 铁律 + 13 反模式 + 归一化百分制。
这是对方法论本身的错误陈述，读者按此判断会得到偏差认知。

同时补了「⏱️ 先看效果（30 秒，零部署）」小节：后端项目无法 30 秒试用是真实痛点，
现在给 4 个免安装入口（真实截图 / 指标库 / 静态资料库 / API 文档地址）。

### 3.2 ATLAS 与 davy — 同一类结构缺陷

两者的 `## 架构` 章节与 mermaid 图都排在 `# 标题` **之前**，
导致 GitHub 首屏先渲染架构图、再渲染主标题，标题不在首屏中央。
已把架构块下移到目录之后，主标题回到首屏首位。

这是本轮发现的**跨项目系统性问题**：凡是按「frontmatter → 架构 → 标题」顺序生成的
README 都有这个问题。以后生成时要注意标题必须在首屏。

### 3.3 SkyNet / davy — 缺失的可复现性

- SkyNet：补 `curl -s http://127.0.0.1:8000/health` 最小验证（含预期输出），
  此前读者无法确认服务是否真的可用
- SkyNet / davy：补语言策略声明（默认简体中文，英文版欢迎 PR），
  避免后续维护者误加 `README.en.md` 破坏一致性

### 3.4 deepsearch / echo — 修正我自己引入的错误

补 Version badge 时，我第一次把 deepsearch 的版本写成 3.3.3
（那是 Spring Boot 父 pom 的版本），实际项目 version 是 1.0.0。
核对 `pom.xml` 后立即改正。

**这正是方法论禁止的行为**——未核实就写数字。已把两个项目的版本号都回源核对：
- deepsearch：`pom.xml` 的 project 级 `<version>` = 1.0.0
- echo：`package.json` 的 `version` = 1.0.0

另外，这两个是**内网 GitLab** 项目，无法使用 GitHub CI/star badge。
选择如实标注 `build: local only`，而不是留空或伪造 CI 通过状态。

## 4. 可复用的经验（写给下一个人）

### 4.1 review.yaml 是最高投入产出比的改进

一份 review.yaml（20 行）比重写整篇 README 有效得多：

- 让 9 条语义铁律从「不参与评分」变成「有据可查的分数」
- 每条 reason 强制写清扣分理由，**逼你承认哪里不够好**
- 结果可复现：`npx github:davyzhong/readme-craft check . --review review.yaml`

### 4.2 N/A 比扣分更诚实

FLOW 的 T11（引用背书）是私有项目，标记 `status: na` 并写明理由，
不因为"没有客户 logo"扣分。SkyNet / davy 的 T11 同理。

**判断标准**：不适用 → N/A；适用但没做好 → 低分。混淆两者会让分数失去意义。

### 4.3 工具的检测边界必须显式披露

本轮 readme-craft 自身加了 `detection` 字段。评审时能清楚看到：
T03 只数 badge 数量和 shields.io 来源，**不判断 badge 指向的检查是否真实可用**。
所以"T03 得 5 分"不等于"badge 反映的项目健康度真实可信"。

### 4.4 首屏结构是最容易犯又最容易修的错误

`frontmatter → ## 架构 → # 标题` 这个顺序在 ATLAS、davy 上都出现了。
规则很简单：**H1 必须是 frontmatter 之后第一个块级元素**。
